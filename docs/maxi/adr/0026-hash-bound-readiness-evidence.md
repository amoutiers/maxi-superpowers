# ADR-0026: Hash-Bound Readiness Evidence

## Context

[0022-fixed-review-boundaries](0022-fixed-review-boundaries.md) establishes
`/maxi:analyze` as the readiness review before implementation, but a passing
`analysis.md` does not currently prove that it reviewed the present spec, plan,
and tasks. Status and timestamps alone cannot detect structural changes, while
ordinary task checkbox progress should not invalidate an otherwise current
review.

Implementation must fail closed when readiness evidence is missing, malformed,
blocked, unsupported, or stale, without changing the ten-state FSM or moving
review ownership.

## Decision Drivers

- Make readiness freshness executable before every new or resumed
  implementation dispatch.
- Detect structural spec or tasks changes and any plan change.
- Avoid invalidation from status/timestamp updates or canonical task checkbox
  progress alone.
- Preserve the fixed review boundaries and existing FSM.

## Considered Options

- **Option A: Versioned hash-bound evidence, selected**
  - ✅ Detects stale inputs deterministically at the implementation boundary.
  - ✅ Ignores only known non-structural pipeline progress.
  - ❌ Requires stamping and verifying an explicit report contract.

- **Option B: Trust status and timestamps**
  - ✅ Adds no new evidence format.
  - ❌ Cannot prove which artifact content the readiness review covered.

- **Option C: Rerun analysis before every dispatch**
  - ✅ Reviews the current artifacts.
  - ❌ Repeats the full audit when unchanged artifacts could be verified
    cheaply.

## Decision

Choose Option A. The `maxi-readiness-v1` contract records structural SHA-256
hashes for `spec.md` and `tasks.md`, plus an exact SHA-256 hash for `plan.md`.
These hashes make readiness freshness executable: `/maxi:implement` verifies
them against the current artifacts before every new or resumed dispatch.

For the structural spec hash, only frontmatter `status` and `updated` are
ignored. For the structural tasks hash, only frontmatter `updated` and canonical
`TNNN` task checkbox progress are ignored. These status/timestamp fields and
canonical task checkbox progress are the only ignored changes. The plan hash is
exact.

`/maxi:analyze` stamps both passing and blocked reports after its allowed status
transition. Verification accepts only a supported, well-formed passing contract
with zero critical issues and matching current hashes. Any other result stops
before implementation mutation or dispatch and requires `/maxi:analyze` again.

This decision complements rather than supersedes
[0022-fixed-review-boundaries](0022-fixed-review-boundaries.md): it makes the
existing readiness boundary current and enforceable without adding a review,
changing its owner, or changing an FSM state.

## Consequences

- **Good:** Initial and resumed implementation cannot use stale readiness
  evidence.
- **Good:** Status transitions, timestamps, and completed task checkboxes do not
  create false staleness.
- **Good:** Review ownership and the ten-state FSM remain unchanged.
- **Bad:** Legacy or manually written analysis reports must be regenerated by
  `/maxi:analyze`.
- **Bad:** Any plan byte change requires a fresh readiness review.

## Confirmation

`tests/check-readiness-contract.sh` verifies stamping, accepted non-structural
changes, and fail-closed stale or malformed evidence.
`tests/check-review-boundaries.sh` and `tests/check-implement-handoff.sh` verify
that analysis stamps the contract and implementation verifies it before every
new or resumed dispatch.
